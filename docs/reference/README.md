# Documentation Map

The repository separates readable source documentation from generated GitHub Pages output. Use this map to find the correct source and avoid editing generated files.

## Public Reader Documentation

The Taxonomy tab on the project page is rendered from these concise, reader-oriented sources. Keep their prose approachable; controlled definitions and annotation rules belong in `docs/reference/`.

| Document | Purpose | Edit directly? |
|---|---|---|
| [`../public/taxonomy.md`](../public/taxonomy.md) | English public explanation of the six taxonomy axes | Yes; update when canonical vocabulary changes |
| [`../public/taxonomy.ja.md`](../public/taxonomy.ja.md) | Japanese public explanation of the six taxonomy axes | Yes; keep structurally aligned with English |

Run `python3 scripts/check_public_taxonomy.py` after taxonomy changes. It checks the public axes, family names, and leaf labels against the canonical reference and executable vocabulary without generating the reader-oriented prose.

## LLM Agents and Automation Maintainers

Start with [`../../AGENTS.md`](../../AGENTS.md). Public operational runbooks live separately under `docs/agent/`:

- [`../agent/daily-curation-workflow.md`](../agent/daily-curation-workflow.md): bounded new-paper discovery, curation, validation, and publication (stable filename; schedule configured externally).
- [`../agent/biweekly-metadata-maintenance.md`](../agent/biweekly-metadata-maintenance.md): signal-driven existing-record maintenance; changed-record bibliography only.
- [`../agent/curation-queue.md`](../agent/curation-queue.md): external shared state, whole-run locking, 20-record budgets, and mandatory exit reports.

Local schedules should keep machine-specific paths, cadence, and private workspace boundaries in the automation prompt rather than adding them to public documentation.

## Generated GitHub Pages Output

The `docs/` root is the GitHub Pages publication root. Do not hand-edit these generated files:

- `index.html`: interactive Project Page, generated by `scripts/build_explorer.py`
- `readme.html`, `readme.ja.html`: rendered README pages, generated by `scripts/build_doc_pages.py`
- `taxonomy.html`, `taxonomy.ja.html`: rendered public taxonomy pages sourced from `docs/public/`, generated by `scripts/build_doc_pages.py`
- `visualizations/*.svg`: generated charts, produced by `scripts/build_visualizations.py`

The explorer source template lives at [`../../templates/explorer.html`](../../templates/explorer.html).

## SEO and Search-Engine Deployment Assets

These files form one deployment group but must remain at the published site root because crawlers and ownership checks request their exact root URLs:

- `robots.txt`: crawler policy and sitemap discovery
- `sitemap.xml`: canonical crawl targets
- `googlecd3652538aa5cebc.html`: Google Search Console ownership verification

Keeping them in `docs/` is a hosting requirement, not a documentation-audience choice.

## Site Identity Asset

`docs/favicon.svg` is a maintained SVG asset matching the explorer header mark, including its light and dark theme colors. The explorer template and rendered documentation template reference it; keep the favicon geometry aligned when changing the header mark.

`docs/favicon.png` (96×96) and `docs/favicon.ico` are raster companions for search engines and browsers. They use the same geometry and light-theme orange as the SVG. Google Search also requires the hostname home page to declare its favicon; a project subdirectory alone cannot set a separate search favicon.
